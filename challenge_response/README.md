# Challenge–Response 안티스푸핑 프로토타입

수어 제스처 인증의 **replay attack 대응 모듈**. 인증할 때마다 시스템이 무작위 동작
3개(손 모양 2개 + 방향 이동 1개)를 요청하고, 사용자가 제한 시간 안에 수행했는지
규칙 기반으로 판정한다. 딥러닝 학습은 없다. MediaPipe 랜드마크 + 기하 계산 +
상태 머신으로 구현했다.

**모든 임계값은 파일럿 영상 52개의 실측 분포에서 나왔다.** 코드에는 임계값 숫자
리터럴이 없고, `configs/challenge_config.json`의 모든 값에 근거 분포가 `_source`로
적혀 있다. 분포가 겹쳐 도출하지 못한 값은 임의로 채우지 않고 `null` + `_unresolved`로
남겼다.

---

## 1. 설치

Python **3.10 또는 3.11**을 쓴다. (mediapipe 0.10.14는 3.12를 지원하지 않는다.)

```bash
cd challenge_response
python -m venv .venv
.venv\Scripts\activate          # Windows
pip install -r requirements.txt
```

`mediapipe==0.10.14`와 `numpy<2`는 고정이다. AI팀이 이 버전으로 기존 제스처
데이터를 처리했으므로 버전을 올리면 랜드마크 좌표가 미세하게 달라져 통합할 때
어긋난다.

`configs/paths.json`의 `video_root`를 촬영 영상 위치로 맞춘다.

## 2. 실행 순서

```bash
python scripts/01_extract_landmarks.py          # 영상 -> data/landmarks/*.npz  (--force로 재생성)
python scripts/02_check_mirror.py               # 좌우 반전 확정 -> paths.json에 기록
python scripts/03_analyze_distributions.py      # 분포 측정 -> reports/
python scripts/04_derive_thresholds.py          # 임계값 도출 -> configs/challenge_config.json
python scripts/05_validate_rules.py             # 혼동 행렬 + SPEC 4.11 목표 대비
python scripts/run_challenge.py --participant P01   # 웹캠 실시간 프로토타입
python scripts/06_analyze_sessions.py           # 실시간 세션 집계 + 파일럿 대비 갭
python scripts/record_negatives.py --participant P01 --window-height 780   # 웹캠 반례 녹화·즉시 평가 (4.4)
pytest                                          # 합성 랜드마크 기반 단위 테스트
```

**02는 03보다 먼저 반드시 실행해야 한다.** 반전 여부를 모르고 분석하면 좌우 이동
판정이 통째로 뒤집힌다.

`run_challenge.py` 키 조작: `q` 종료, `r` 재시작, `s` 참가자 ID 입력.
성공·실패 영상을 모두 `data/sessions/`에 저장한다. 실패 영상이 규칙 개선의 재료다.

화면 구성:
- 창은 **[상단 띠 | 카메라 영상 + 오른쪽 패널 | 하단 띠]** 로 나뉜다. 안내·계측 패널이
  카메라 영상을 가리지 않는다. (예전에는 상단 띠가 640×480 영상의 위쪽 132px를 덮어
  손이 화면 밖으로 나간 것처럼 보였다.)
- 창은 끌어서 크기를 바꿀 수 있고, 시작 시 모니터 세로의 90%로 뜬다
  (`--window-height`로 지정). `--capture 1280x720`으로 카메라 해상도를 요청할 수 있다.
  노트북 웹캠에서 확인한 결과 720p는 좌우만 넓어지고 세로 시야는 640×480과 같다.
- 손의 윤곽이 영상 가장자리에서 **손 크기(손목–중지 MCP)의 1/4** 안으로 들어오면 그쪽
  가장자리에 빨간 띠와 경고 문구가 뜬다. 가장자리에 붙어 있다가 손을 놓치면 "화면 밖으로
  나갔습니다"로 바뀐다. 이 여유 거리는 판정 임계값이 아니라 안내용이며, 실행 로그의 프레임
  줄에 `edge=`로 남는다.
- 웹캠 영상을 **거울처럼 좌우 반전해** 보여준다. 화면에 보이는 방향으로 움직이면 된다.
- 오른쪽 **안내 패널**에 요청 동작을 그림으로 보여준다. 손 모양은 어느 손가락을
  펴야 하는지, 이동은 어느 쪽으로 가야 하는지 화살표로 나온다. 아래쪽 작은 아이콘
  3개는 전체 단계이며 현재 단계가 노란 테두리로 표시된다.
- 손 그림은 MediaPipe 21점 연결 구조로 그린다(`scripts/hand_sketch.py`).
  펴는 손가락은 초록, 접는 손가락은 회색이다.
- 안내 그림은 `SHAPE_PATTERNS`와 config의 `direction_map`에서 직접 만든다. 그림과
  판정 규칙이 어긋날 수 없고, `tests/test_guide_overlay.py`가 이를 검증한다.
- 엄지는 판정에서 빼므로 안내 그림에서도 회색으로만 그린다.
- 단계 전환 직후 이전 손 모양에서 벗어나야 할 때는 **"손을 한 번 바꿨다가 다시
  해주세요"** 안내가 뜨고, 시간 막대가 주황색 이탈 진행도로 바뀐다. 이 동안은
  제한 시간이 흐르지 않는다. (아래 4.3)
- **이동 단계에서는 오른쪽 패널(안내 그림 아래)에 판정 계측이 뜬다.** 두 관문의 현재 값을 그대로
  보여준다. 임계값을 짐작해서 바꾸기 전에 무엇이 막고 있는지부터 눈으로 본다.

```
window       15/15                    O
gate1 disp   0.42 / 0.169  x2.49      O     <- 변위 크기 / 임계값 / 배수
gate2 axis   2.10 / 4.19   x0.50      X     <- 주축비 / 임계값 / 배수
axis         y+   -> NONE                   <- 주축과 부호, 최종 라벨
```

시도가 끝날 때마다 **이번 실행의 사유별 통계**를 화면(결과 화면 오른쪽 패널)과 콘솔에
같이 띄운다. 여러 번 돌린 뒤 무엇이 걸림돌인지 바로 보기 위한 것이다.

```
이번 실행 20회 중 통과 7회 (35%)
  중앙 소요시간 2999ms, 재시도 사용 3회
  실패 사유                  횟수   단계별
  WRONG_SHAPE             7   1단계 5회, 3단계 2회
  HAND_LOST               3   2단계 3회
  ACTION_TIMEOUT          2   3단계 2회
```

사유뿐 아니라 **몇 단계에서 막혔는지**도 센다. 같은 `WRONG_SHAPE`라도 1단계에
몰리면 사용자가 시작 자세를 잡을 시간이 부족한 것이고, 3단계에 몰리면 앞 단계에서
시간을 다 쓴 것이라 원인이 다르다.

통계는 **프로세스 단위**로 쌓인다. `q`로 끄면 초기화되므로, 한 세션에서 연속으로
돌린 뒤 종료 시 나오는 최종 요약을 보면 된다. 개별 시도 기록은 계속
`data/sessions/results.csv`에 누적되므로 나중에 다시 집계할 수 있다.

## 3. config 항목

### `configs/paths.json`
| 항목 | 설명 |
|---|---|
| `video_root` | 파일럿 영상 위치 (저장소 바깥) |
| `landmark_cache` | 랜드마크 `.npz` 캐시 |
| `session_out` | 실시간 세션 영상·랜드마크·결과 CSV |
| `report_out` | 분포 리포트 |
| `mirror_flip` | 참가자별 좌우 반전 여부. **02가 자동 기록한다** |
| `mirror_flip_flicker_ratio` | handedness가 프레임마다 흔들린 비율 |

### `configs/extraction.json`
MediaPipe Hands 설정. 판정 임계값이 아니라 추출 설정이다. SPEC 4.1에 고정.

### `configs/derivation_policy.json`
임계값 자체가 아니라 **"분포에서 임계값을 어떻게 뽑을지"** 를 적은 파일.
04가 이걸 읽어서 config를 만든다.

| 항목 | 설명 |
|---|---|
| `positive_percentile` / `negative_percentile` | 정상 p5를 통과시키고 경계 p95를 거르는 규칙 |
| `separation_margin_ratio` | 틈이 있을 때 임계값을 틈의 몇 지점에 놓을지 (0.5 = 가운데) |
| `motion_edge_trim_windows` | 영상 앞뒤 손 진입/이탈 구간을 몇 윈도우 잘라낼지 |
| `unresolvable_shape_negatives` | 규칙으로 분리 불가 확정된 반례. 다른 임계값 도출 근거에서 제외 |
| `targets` | SPEC 4.11 목표. **채점에만 쓰고 임계값을 정하는 데는 쓰지 않는다** |
| `max_retries`, `coordinate_frame` | 측정으로 정할 수 없는 정책 값. `_source`에 '측정값 아님' 명시 |
| `fist_tip_wrist_gate` | FIST에 손끝-손목 거리 게이트를 걸지 여부. OPEN_PALM에는 걸지 않는다 (5.1) |
| `lost_frames_min_samples` | 정상 영상 중간 끊김이 이보다 적으면 `max_lost_frames`를 도출하지 않는다 |
| `max_lost_frames_provisional` | 위 경우 쓰는 임시값 38. **측정값 아님.** 2명 기준 도출값을 유지한 것 |

### `configs/challenge_config.json` (04가 생성)

아래 표의 값은 2명 기준(2026-09-07)이다. 5명 기준 값과 근거는
`configs/challenge_config.json`의 `_source`를 본다. 5명 기준에서 새로 생긴 항목:

- `frame_reference_fps`: 파일럿 영상 fps 중앙값(30.0). `shape_hold_frames`·`escape_frames`·
  `max_lost_frames`·이동 윈도우 프레임 수는 이 fps에서 센 값이다. **상태 머신은 프레임 수를
  세지 않고 관측 시각으로 판정한다**(`FrameSpan`, `TimeWindow`). 웹캠이 약 20fps로 돌면서
  프레임 수 기준으로는 윈도우 600ms가 874ms, 유지 233ms가 340ms, 끊김 1267ms가 1845ms로
  늘어났기 때문이다. 기준 fps로 들어오면 프레임 수로 센 것과 결과가 같다
  (`tests/test_time_based_frames.py`). 20fps의 원인은 MediaPipe(model_complexity 1, 프레임당
  약 50~57ms)라 SPEC 4.1 설정을 바꾸지 않는 한 30fps로 올릴 수 없다.
- `fist_max_tip_wrist_ratio`: FIST로 인정하는 손끝-손목 거리/손 크기 상한 (5.1)
- `timing.per_action_timeout_ms`: 손 모양 시간은 **손이 처음 검출된 뒤부터** 재고,
  이동은 **MOVE 영상별 획 시간을 영상마다 1건씩** 넣는다. 예전처럼 대표값 1건만 넣으면
  손 모양 영상이 늘수록 p95가 손 모양 쪽으로 끌려 내려가 500ms까지 떨어졌다.
- `tracking.max_lost_frames`: 5명 영상은 중간 끊김이 1건뿐이라 도출하지 않고
  `_unresolved`에 기록한 뒤 임시값 38을 쓴다.
- `movement.direction_map`: **튕기는 방식(정지 -> 한 방향 -> 제자리 정지)으로 찍은
  영상만** 첫 획 방향 표결에 쓴다. 판별 조건은 `_source.direction_clip_rule`, 뺀 영상과
  사유는 `_source.direction_excluded_clips`와 `reports/direction_votes.csv`에 있다.
  변위·축비 통계에는 멈춤 없는 왕복 영상도 계속 쓴다. (5.8)
- `movement.rest_displacement_ratio`: NEG_shake 윈도우 변위 p95. 촬영 방식 판별(04,
  05)에만 쓰고 실시간 판정에는 쓰지 않는다.

| 항목 | 값 | 근거 |
|---|---|---|
| `angle_space` | `image_iso` | 펴짐/접힘 분리폭이 `world`(45.5°)보다 넓음(67.1°) |
| `finger_extended_angle.others` | 132.6° | 펴야 하는 손가락 p5=166.1° / 접어야 하는 손가락 p95=99.0° |
| `finger_extended_angle.thumb` | 145.2° | OPEN_PALM 엄지 p5=151.1° / FIST 엄지 p95=139.3° |
| `shape_hold_frames` | 9 | 손 모양 반례 오검출 연속길이 p95=7.8프레임 +1 |
| `shape_confidence_margin_deg` | 33.5 | 펴짐/접힘 분포 틈 67.1°의 절반 |
| `shape_confidence_min` | **null** | 도출 실패 (아래 5장) |
| `escape_frames` | 13 | 손 모양 유지 중 오검출 구간 **최대치** 12프레임 +1 (아래 4.3) |
| `movement.window_ms` | 500 | 획 1회 소요시간 p5=524ms |
| `movement.min_displacement_ratio` | 0.169 | MOVE 영상 p75 변위의 p5=0.280 / NEG_shake p95=0.057 |
| `movement.axis_dominance_ratio` | 4.194 | MOVE 획 주축비 p5=5.34 / NEG_diagonal p95=3.05 |
| `movement.max_duration_ms` | 2000 | 획 1회 소요시간 p95=1915ms |
| `movement.direction_map` | 좌=x−, 우=x+, 상=y−, 하=y+ | 16개 영상의 첫 획 방향 만장일치 |
| `timing.per_action_timeout_ms` | 2500 | 정답 유지까지 걸린 시간·획 시간 p95=2120ms |
| `timing.total_timeout_ms` | 7500 | 단계 시간 × 3 |
| `timing.max_retries` | 1 | **측정값 아님.** 프로토콜 정책 |
| `tracking.max_lost_frames` | 38 | 정상 영상 중간 끊김 p95=9.1 / NEG_exit 중간 끊김 p5=66.9 |
| `tracking.min_detection_score` | 0.857 | 정상 영상 detection_score p5 |
| `coordinate_frame` | `mirrored` | **측정값 아님.** 화면을 보는 사용자 기준으로 판정 (SPEC 4.5) |

`_unresolved`에 값이 있으면 그 항목은 분포가 겹쳐 도출하지 못한 것이다.
`run_challenge.py`가 실행 시 경고를 띄운다.

## 4. 검증 결과 (`05_validate_rules.py`)

SPEC 4.11 목표 10개 중 **9개 달성** (5명 기준, 2026-09-16).

| 항목 | 2명 기준 | 5명 기준 | 목표 | |
|---|---|---|---|---|
| OPEN_PALM 정확 판정 | 99.8% | 99.9% | ≥90% | 달성 |
| FIST 정확 판정 | 99.3% | 98.2% | ≥90% | 달성 |
| INDEX 정확 판정 | 99.8% | 99.3% | ≥90% | 달성 |
| TWO_FINGERS 정확 판정 | 98.1% | 98.2% | ≥90% | 달성 |
| NEG_halffist → OPEN_PALM/FIST | 91.2% | **20.6%** | <5% | **미달** (5.1) |
| NEG_threefingers → TWO_FINGERS | 0.3% | 0.6% | <5% | 달성 |
| NEG_indexring → TWO_FINGERS | 1.9% | 0.0% | <5% | 달성 |
| MOVE_* 이동 검출 | 왕복 3회 16/16영상 | **편도 첫 검출 26/26회** | 전부 | 달성 (아래) |
| NEG_shake 이동 검출 | 0회 | 0회 | 0회 | 달성 |
| NEG_diagonal 요청 1회 통과율 | – | 15.0% (3/20쌍) | ≤25% | 달성 (아래) |
| (참고) NEG_diagonal 단일 방향 확정 윈도우 | 1.1% | 3.6% | <20% | 채점 제외 |

**대각선 목표를 윈도우 비율에서 요청 1회 통과율로 바꿨다 (2026-09-16).** 실제 인증은
요청 1회(단계 2초 × (1 + 재시도 1) = 4초) 안에 한 번만 걸리면 통과한다. 윈도우 비율이
20% 미만이어도 요청 방향이 한 번 잡히면 뚫린다. 지금은 NEG_diagonal 영상 × 요청 방향
쌍마다 **실제 상태 머신(제한 시간·재시도·추적 규칙 그대로)** 으로 통과 여부를 재고
(`negative_eval.request_passes`), 요청은 손이 처음 잡힌 순간 시작한다.

목표 25%는 측정값이 아니다. `derivation_policy.targets.diagonal_request_pass_basis = "chance"`
로, 1/(direction_map 방향 수)다. 대각선 반례가 한 방향을 무작위로 찍는 것보다 더 잘 통과하면
안 된다는 뜻이다. 숫자로 고정하려면 `diagonal_request_pass_max`를 둔다.

| 같은 방식으로 잰 대상 | 통과 쌍 | 한 방향 이상 뚫린 영상 |
|---|---|---|
| 파일럿 NEG_diagonal (폰, 영상 전체) | 3/20 (15%) | 2/5 (P03 UP·DOWN, P05 DOWN) |
| 파일럿 NEG_diagonal (진입·이탈 구간 제외) | 4/20 (20%) | 3/5 |
| 웹캠 NEG_diagonal (P01 5회, 4.4) | 4/20 (20%) | 3/5 |

**웹캠만의 문제가 아니라 파일럿에서도 원래 비슷했다.** 윈도우 비율(파일럿 3.6%, 웹캠 7.2%)로는
이 차이가 드러나지 않았다. 같은 측정으로 정상 이동이 반대 방향 요청을 통과하는 문제도
드러났다(5.10).

**MOVE 목표를 왕복에서 편도로 바꿨다 (2026-09-16).** 예전 목표 "라벨 방향으로 3회
검출"은 파일럿 촬영 방식(왕복 3회)을 전제로 한 것이라 실사용과 맞지 않았다. 실시간
이동 단계는 정지 상태에서 요청 방향으로 한 번 움직이는 것을 판정한다. 지금 05는
튕기는 방식 영상을 "정지 -> 한 방향 이동 -> 제자리 정지" 구간으로 나누고, 구간마다
**처음 검출된 방향**이 라벨과 같은지 센다. 구간 안에서 아무것도 검출되지 않으면 실패다.
멈춤 없는 왕복 영상(27/40)은 편도 시도로 나눌 수 없어 평가하지 않는다. 검출 사건
전체(왕복 기준)는 참고로만 출력한다. 근거가 좁다는 한계는 5.8에 있다.

### 4.1 실기기(웹캠) 확인

`run_challenge.py`를 실제 웹캠으로 돌려 확인했다. 초기 버전은 20회 중 2회만
통과했고, 실패 11건 중 7건이 "손을 든 순간의 모양이 요청과 달라 0.3~0.7초 만에
종료"된 경우였다. 아래 두 가지를 고친 뒤 4회 중 3회 통과했고, 남은 1회는 카메라
앞에 손이 없던 경우(`HAND_NOT_FOUND`)다.

**(1) 단계별 유예 시간.** 틀린 동작을 즉시 실패로 보지 않고
`per_action_timeout_ms`(2500ms)까지 기다린 뒤, 그동안 무엇을 했는지로 사유를
정한다. 사용자가 요청을 읽고 손 모양을 바꿀 시간이 생긴다. `FailReason` 종류는
그대로이고 새 임계값도 만들지 않는다.

| 그동안 한 것 | 사유 |
|---|---|
| 다른 선언된 손 모양을 유지 | `WRONG_SHAPE` |
| 그게 뒤 단계 동작이었음 | `WRONG_ORDER` |
| 요청과 다른 방향으로 이동 | `WRONG_DIRECTION` |
| 아무것도 확정 못 함 | `ACTION_TIMEOUT` |

이동 단계에도 같은 규칙이 필요하다. 왕복 동작 중에는 반대 방향 획이 반드시
지나가므로, 즉시 실패시키면 정상 수행도 통과할 수 없다.

**(2) 좌우 반전 이중 적용 수정.** 아래 5.6 참조.

### 4.2 실시간 세션 집계 (`06_analyze_sessions.py`)

`data/sessions/results.csv`를 읽어 무엇이 병목인지 집계한다.

- 실패 사유별 횟수와 **막힌 단계**
- 요청 동작별 통과율 (어느 동작이 유독 안 되는지)
- **이동 관문별 통과 비율**: 평가된 윈도우 중 1번 관문(변위 크기)을 통과한 비율,
  그중 2번 관문(주축 지배)을 통과한 비율
- 시도 단위 병목: 1번을 한 번도 못 넘은 횟수 / 1번은 넘었지만 2번에서 막힌 횟수
- **파일럿 촬영 vs 실시간 사용 비교**

마지막 항목이 핵심이다. 파일럿 영상은 폰을 거치하고 의식적으로 반듯하게 찍은
것이라 실시간 사용 조건과 다를 수 있다. 이 스크립트는 파일럿 영상에도 실시간과
**같은 윈도우 길이·같은 진입/이탈 제외 규칙·같은 관문 조건**을 적용해 다시 재고,
두 분포를 나란히 놓는다. 갭이 있다면 숫자로 드러난다.

주축비는 최대치와 중앙값을 같이 본다. 부축 변위가 0에 가까운 윈도우 하나가
최대치를 수천 배로 끌어올려 분포 비교에 쓸 수 없기 때문이다. 주축비는 변위
관문을 통과한 윈도우에서만 모은다. 거의 안 움직인 윈도우의 주축비는 잡음이다.

`results.csv`에는 그때의 임계값(`move_min_disp_threshold`,
`move_axis_threshold`, `move_window_ms`)도 같이 적힌다. 나중에 임계값이 바뀌어도
과거 기록을 해석할 수 있다.

### 4.4 웹캠 반례 녹화 (`record_negatives.py`)

파일럿 반례(NEG_shake/diagonal/exit)는 폰 30fps 영상이라 웹캠 실사용 조건과 다르다.
실시간 34회에서 통과한 이동의 최대 변위비 중앙값이 0.568로 파일럿(p5=0.631)보다 작아,
**같은 크기로 흔들면 이동으로 인정되는지** 웹캠으로 직접 확인하려고 만들었다.

- 흔들기·대각선·손 이탈을 종류별 5회(`--takes`) 녹화한다. SPACE → 3초 카운트다운 →
  녹화(최대 `total_timeout_ms`, 한 Challenge 전체 시간) → 결과. `r` 다시 찍기, `n` 건너뛰기.
- 녹화 중 오른쪽 패널에 **이번 흔들기의 최대 변위비와 비교 기준(이번 규칙 버전에서 통과한
  이동의 최대 변위비 중앙값, `results.csv`에서 계산)** 이 나란히 뜬다. 기준 이상이면 노란색.
- 평가는 `core/negative_eval.py`가 한다. 상태 머신에 **어떤 판정 라벨과도 일치하지 않는 이동
  요청**을 주고 녹화 전체를 넣으므로, 점수 게이트·손 놓침·시간 기준 윈도우가 실사용과 똑같이
  적용된다(시간 제한만 끈다). 윈도우마다 나온 이동 라벨이 "그 방향을 요청받았다면 통과했을"
  순간이다. 손이 처음 잡히기 전 프레임은 넣지 않는다.
- 판정 목표는 `derivation_policy.targets`를 그대로 쓴다. 흔들기: 이동 인정 0회. 대각선: 요청
  1회 통과율 25% 이하(4장, 윈도우 비율은 참고로 함께 표시). 손 이탈: SPEC 목표가 없어 "손이
  사라지기 전 이동 인정 0회"를 참고로 본다(5.9).

**P01 웹캠 반례 15회 결과와 판단 (2026-09-16)**

| 종류 | 결과 | 최대 변위비 | 판단 |
|---|---|---|---|
| 흔들기 | 이동 인정 1/5회 | 0.05~0.23 | **수용** |
| 대각선 | 요청 1회 통과 4/20쌍 (20%), 참고 윈도우 비율 0~19.8% | 1.36~1.98 | 목표 달성 (4장) |
| 손 이탈 | 사라지기 전 이동 인정 3/5회 | 0.21~2.12 | **정상 이동으로 수용** (5.9) |

- **흔들기 수용.** NEG_shake의 정의는 "제자리 손떨림"이고 이번 녹화가 그 정의에 맞다. 5회
  모두 변위 관문에서 막혔고(윈도우 74~96개), 통과한 이동 크기(최대 변위비 중앙값 0.568)로
  흔드는 것은 손떨림이 아니라 왕복 이동이라 다른 동작이다.
  **다만 1회(`P01_NEG_shake_01`)는 최대 변위비 0.230으로 `min_displacement_ratio` 0.226을
  0.004 차이로 넘었고, 그 윈도우의 축비 4.3이 축비 관문(3.634)도 넘어 UP으로 인정됐다.**
  손떨림과 이동 사이의 여유가 이 사람·이 조건에서는 거의 없다는 뜻이다. 손떨림이 더 큰
  사용자에서는 흔들기가 이동으로 새어 들어올 수 있으니 참가자가 늘면 다시 녹화한다.
- 저장: `data/negatives_live/{참가자}_NEG_{종류}_{번호}.mp4/.npz`, `results.csv`(다시 찍으면

  임계값이 바뀌면 `negative_eval.observations_from_npz`로 저장본을 다시 평가할 수 있다.

### 4.3 단계 전환 시 이전 손 모양 이탈 관문

**보안 문제였다.** `MOVE_*`는 손바닥을 편 채로 수행하므로 이동이 끝난 시점의 손은
이미 `OPEN_PALM`이다. 다음 단계가 `OPEN_PALM`이면 사용자가 아무것도 하지 않아도
즉시 통과됐다. Challenge가 "요청에 반응했는지"를 확인하지 못하게 되고, 공격자도
손바닥 편 영상 하나로 그 단계를 공짜로 넘길 수 있다.

각 손 모양 단계에 진입할 때 **직전 단계 종료 시점의 손 모양**을 `escape_from`으로
받고, 그 모양이 아닌 프레임이 `escape_frames`만큼 **연속으로** 관측된 뒤에야
판정을 시작한다. 관문이 닫혀 있는 동안은 제한 시간을 소모하지 않는다.

**이동 단계에는 걸지 않는다.** 이동은 단계 전환 때 판정 윈도우를 비우므로 정지한
손으로는 변위가 나오지 않고, Challenge에 이동 단계는 하나뿐이라 "이전 단계가 이미
이동을 만족시키는" 경우 자체가 생기지 않는다. 이동 앞에 관문을 걸면 편 손으로
하는 이동을 하려고 주먹을 쥐었다 펴야 해서 얻는 것 없이 불편해진다.

`escape_frames`의 근거는 **손 모양을 유지하는 동안 생기는 오검출 구간의 길이**다.
이 값이 잡음보다 짧으면 순간 오검출만으로 관문이 열려 방어가 무력해진다. 파일럿
영상의 손 모양 4종에서 라벨이 정답과 다른 구간을 세면 14개가 나온다.

| 구간 수 | p50 | p95 | 최대 |
|---|---|---|---|
| 14 | 1 | 8.1 | 12 |

**이 항목만 최대치 기준으로 정한다 (`escape_frames = 12 + 1 = 13`).** 다른
임계값은 `negative_percentile`(p95)로 나눈다. 그건 사용성 기준이라 드물게
어긋나도 사용자가 한 번 더 시도하면 된다. 이탈 관문은 성격이 다르다. 잡음 구간
하나가 관문을 열면 그 시도는 방어가 통째로 무력해진다. p95=8.1로 잡으면 관측된
14개 중 1개 구간이 관문을 혼자 열 수 있다.

이 규칙은 `derivation_policy.json`의 `escape_frames_basis`에 있다(`"max"` 또는
`"percentile"`). 코드에 박혀 있지 않다.

정상적인 손 모양 변경에 걸리는 시간은 파일럿 영상으로 잴 수 없다(각 영상이 한
모양만 유지한다). 그래서 근거에는 잡음 쪽만 들어갔고, 반대쪽은 실사용 세션이
쌓인 뒤 다시 봐야 한다. 표본이 14개뿐이라는 경고를 04가 실행 시 출력한다.

`results.csv`에 `rule_version`과 `escape_frames`가 기록되므로 변경 전후를 갈라서
비교할 수 있다. `06_analyze_sessions.py`가 버전별 통과율을 먼저 출력하고,
`--rule-version`으로 한 버전만 볼 수 있다.

## 5. 알려진 한계

### 5.1 `NEG_halffist`: FIST 쪽은 손끝 거리 게이트로 막고, OPEN_PALM 쪽은 수용한다

| 기준 | halffist→FIST | halffist→OPEN_PALM | 합계 (목표 <5%) |
|---|---|---|---|
| 2명 (P01 재촬영 전, P05) | 86.5% | 4.6% | 91.2% |
| 5명, 각도 규칙만 | 72.0% | 20.0% | 92.0% |
| **5명, FIST 손끝 거리 게이트 적용 (현재)** | **0.6%** | 20.0% | **20.6%** |

**반쯤 쥐는 방식이 사람마다 두 가지다.** 2명일 때는 둘 다 첫 번째 방식이라 드러나지 않았다.

| 방식 | 참가자 | 각도 규칙의 판정 |
|---|---|---|
| 손가락 중간 마디(PIP)를 굽힘 | P01, P05 | 98~100%가 FIST |
| 손가락은 편 채 손바닥 쪽 관절(MCP)만 굽힘 | P02, P03, P04 | 30~40%가 OPEN_PALM |

각도 규칙은 MCP-PIP-TIP 사잇각만 보므로 두 번째 방식의 손을 편 손으로 읽는다.

**FIST 쪽: 손끝-손목 거리 게이트 (`fist_max_tip_wrist_ratio`).** 엄지를 뺀 4손끝과
손목의 평균 거리를 손 크기(손목-중지 MCP)로 나눈 값이다. 반쯤 쥔 손은 두 방식 모두
손끝이 주먹보다 손목에서 멀다. 각도 패턴이 FIST여도 이 값이 상한 이상이면 UNKNOWN이다.

- 5명 전원에서 FIST와 NEG_halffist 사이에 틈이 있었다(참가자를 하나씩 빼고 나머지로
  기준을 정하면 4명은 오판정 0%, P01만 18%).
- 04가 FIST 정답 프레임 p95=0.835와 FIST로 판정된 NEG_halffist 프레임 p5=0.983
  사이에서 0.909를 뽑았다. FIST 정확 판정은 98.2%로 게이트 전과 같다.
- **주의: 위 0.6%는 같은 영상으로 임계값을 정하고 평가한 낙관적 수치다.** 새
  참가자에서는 더 샐 수 있다. `_source_fist_max_tip_wrist_ratio`에도 같은 문구가 있다.

**OPEN_PALM 쪽: 적용하지 않는다 (수용).** 같은 특징으로 OPEN_PALM에도 하한을 걸어
봤지만 P03 22%, P04 17%가 여전히 통과했고, 정상 OPEN_PALM 정답률이 99.9% → 89.4%로
떨어졌다. 얻는 것보다 잃는 것이 크다. `derivation_policy.json`의
`fist_tip_wrist_gate_note`에 이 결정을 적었다.

아래는 2명 기준으로 각도 규칙의 한계를 확인한 분석이다.

**원인은 임계값 조정으로 해결되지 않는다.** 두 분포가 실제로 겹친다.

| 집단 | p5 | p50 | p95 |
|---|---|---|---|
| FIST 4손가락 관절 각도 | 15.7° | 43.3° | 90.5° |
| NEG_halffist 4손가락 관절 각도 | 46.8° | 83.6° | 137.0° |
| 프레임별 **가장 펴진** 손가락 — FIST | 44.2° | 51.8° | **106.1°** |
| 프레임별 **가장 펴진** 손가락 — halffist | **69.8°** | 96.6° | 143.3° |

프레임 단위로 봐도 **36.3° 겹친다**. 임계값을 훑어본 결과:

| 임계값 | halffist→FIST | halffist→OPEN_PALM | 합계 오검출 |
|---|---|---|---|
| 110° | 64.8% | 12.5% | 77.3% |
| 132.6° (채택) | 86.5% | 4.6% | 91.1% |
| 150° | 98.3% | 0.0% | 98.3% |

임계값을 낮추면 FIST 오인은 줄지만 OPEN_PALM 오인이 늘어 총 오검출은 오히려
나빠진다. **어떤 값에서도 5% 미만이 되지 않는다.**

구조적 이유: FIST 패턴은 네 손가락이 "펴지지 않음"만 요구한다. 반쯤 접힌 손은
정의상 여기에 걸린다.

**엄지를 판정에 넣어도 해결되지 않는다.** 히스토그램에서는 엄지가 갈라 보이지만
참가자별로 보면 겹친다.

| 엄지 각도 | P01 | P05 |
|---|---|---|
| FIST p50 | 120.0° | 76.6° |
| FIST p95 | 157.4° | 99.2° |
| NEG_halffist p5 | 136.4° | 132.3° |

P01은 주먹을 쥘 때 엄지를 펴고 P05는 접는다. 참가자별 최악 기준으로
**틈이 −25.1°** 다. SPEC 4.6이 엄지를 판정에서 뺀 이유가 데이터로 확인됐다.

**현재 판단(OPEN_PALM 쪽 수용):** 반쯤 쥔 손이 OPEN_PALM으로 새는 것은 보안상
문제가 되지 않는다. Challenge가 3단계이고 손 모양 2개는 서로 다르게 뽑히므로, 반쯤
쥔 손으로 OPEN_PALM 단계 하나를 통과해도 나머지 두 단계(다른 손 모양 1개 + 방향
이동 1개)를 통과해야 한다. 이동 단계는 `NEG_shake` 0회·`NEG_diagonal` 3.6%로 방어가
확인됐다.

**남은 과제:** OPEN_PALM 쪽까지 막으려면 손끝 거리 외의 특징(손가락별 MCP 굽힘 등)이나
이 경계 케이스용 소형 분류기가 필요하다. 촬영 가이드(7장)에 두 쥐는 방식을 명시했으니
참가자가 늘면 다시 잰다.

### 5.2 `shape_confidence_min`을 도출하지 못했다

정답 프레임의 신뢰도 p5=0.811인데 NEG 오검출 프레임의 신뢰도 p95=0.897로 더 높다.
오검출 프레임(주로 `NEG_indexring` 1.9%)은 손가락 상태 자체는 뚜렷하고 조합만
정상 패턴과 겹치는 경우라, 신뢰도로는 걸러낼 수 없다.

`null`로 두었고 상태 머신은 이를 **게이트 없음(0.0)** 으로 해석한다. 임의의 값을
넣지 않았다.

### 5.3 P01 영상의 검출률이 낮다

P05는 26개 전부 100% 검출인데 P01은 26개 중 25개가 95% 미만이다. 특히
`P01_FIST_near` 2.8%, `P01_FIST_far` 2.2%. 프레임을 확인한 결과 손 모양과
프레이밍은 정상이고 **영상이 심하게 뿌옇게 날아간(저대비) 상태**다.

그 결과 FIST 표본 703프레임 중 P01 몫이 163개뿐이라, **FIST 관련 분포는 사실상
P05 한 명의 데이터**다. 참가자 2명은 임계값 일반화에 부족하며, 특히 엄지처럼
개인차가 큰 특징은 더 그렇다.

`dark` 조건의 검출 실패율(6.9%)이 `near`(12.0%)보다 오히려 낮았다. 조명보다
촬영 품질·개인차가 지배적이다.

### 5.4 영상 회전 메타데이터를 반드시 적용해야 한다

촬영 영상은 컨테이너 회전값을 갖고 있는데(P01=270°, P02=90°, P03=90°, P04=90°,
P05=270°, 2026-09-15 실측. 재촬영 전 P01은 90°였다. 2026-09-16 재촬영한
P02_MOVE_LEFT/RIGHT 4개는 원본 프레임이 이미 세로라 0°다) OpenCV는 기본적으로
적용하지 않는다. 끄고 읽으면 손이 옆으로 누운 프레임이 나와 **상하/좌우 이동 축이
통째로 뒤바뀌고** MediaPipe 검출률도 떨어진다. `landmark_io.extract_clip`이
`CAP_PROP_ORIENTATION_AUTO`를 켜고 회전값을 캐시에 기록한다. 다른 기기 영상을
추가할 때 이 값을 반드시 확인할 것.

### 5.5 이동 분석은 영상 앞뒤를 잘라내야 한다

영상 앞뒤에는 손이 화면으로 들어오고 나가는 큰 동작이 들어 있다. 이걸 포함하면
- `NEG_shake`의 변위가 0.04 → 1.64로 뛰어 흔들기와 이동을 구분할 수 없게 되고,
- P01의 `MOVE_LEFT/RIGHT`가 세로축 이동으로 잘못 보인다(축비 1.11~1.65).

첫/마지막 검출에서 1윈도우씩 잘라내면 16개 MOVE 영상 전부가 기대한 축으로
정렬된다(축비 3.09~9.94). 실시간에서는 `WAIT_HAND` 이전과 `HAND_LOST` 이후를
판정하지 않으므로 같은 조건이다.

### 5.6 좌우 반전은 한 번만 적용해야 한다

거울 화면과 `coordinate_frame: "mirrored"`가 겹치면 좌우 판정이 통째로 뒤집힌다.
초기 구현은 뒤집은 프레임을 MediaPipe에 넣고 config의 반전까지 적용해 반전이 두 번
걸렸다. `MOVE_UP/DOWN`은 영향을 받지 않아 상하 이동만 테스트했을 때는 드러나지
않았다.

현재 구현은 이렇게 나눈다.

| | 좌표계 | 이유 |
|---|---|---|
| MediaPipe 입력 | **원본** | handedness가 반대로 나오지 않게 |
| 저장 영상·랜드마크 | **원본** | 파일럿 영상과 같은 좌표계여야 함께 분석 가능 |
| 화면 표시·랜드마크 오버레이 | 거울(x → 1−x) | 사용자가 자연스럽게 인식 |
| 판정 | config의 `coordinate_frame` | 반전은 `movement_detector` 안에서 한 번만 |

안내 화살표 방향은 `guide_overlay.screen_direction()`이 이 계산을 한 곳에서
처리하므로, 화살표와 판정이 항상 같은 방향을 가리킨다.

### 5.7 1단계에는 이탈 관문이 없다

이탈 관문은 **직전 단계 종료 시점의 손 모양**을 기준으로 동작한다. 1단계는 직전
단계가 없어 `escape_from`을 정할 수 없다. 따라서 Challenge 시작 시점에 이미
1단계 손 모양을 하고 있으면 그 단계는 그대로 통과된다.

막으려면 `WAIT_HAND`에서 손이 처음 잡힌 시점의 모양을 `escape_from`으로 삼으면
된다. 하지만 그러면 **모든 사용자가 매번 인증을 시작하기 전에 손을 한 번 바꿔야**
한다.

**판단: 넣지 않는다.** 매번 시작 자세를 요구하는 비용이, 3단계 중 1단계가 공짜인
것보다 크다고 봤다. 2·3단계에는 관문이 걸려 있으므로 정지된 손 하나로 Challenge
전체를 통과할 수는 없다.

### 5.8 이동 방향과 편도 검증의 근거가 좁다

`direction_map`과 05의 편도 목표는 **튕기는 방식으로 찍힌 13/40개 영상**에만 기댄다.

| 동작 | 표결 영상 | 참가자 |
|---|---|---|
| MOVE_LEFT | 4/4 일치 | P01, P02, P05 |
| MOVE_RIGHT | 5/5 일치 | P01, P02, P05 |
| MOVE_UP | 2/2 일치 | **P05만** |
| MOVE_DOWN | 2/2 일치 | **P05만** |

- **상하 방향은 사실상 한 명의 데이터다.** 화면 좌표에서 위=y−, 아래=y+는 영상 좌표계
  정의와 맞아 틀릴 가능성은 낮지만, 측정 근거로는 약하다.
- **판별 규칙은 같은 데이터를 보면서 세 번 고쳐 정했다.** 처음 규칙(정지를 판정기의
  변위 하한으로 판단, 이웃한 정지끼리 위치 비교)은 궤적상 명백한 튕기기를 놓치거나
  멈춤 없는 왕복을 받아들였다. 최종 규칙은 정지를 NEG_shake p95로, 복귀를 주축 거리로
  잰다. 새 숫자는 없지만 규칙 선택 자체가 이 데이터에 맞춰졌을 수 있다.
- P03 재촬영본(좌우·상)은 궤적상 튕기는 방식이지만 규칙에서 빠졌다. 영상이 움직이는
  중에 시작하거나(좌우), 획 사이에 출발점 반대편으로 넘어가기(상) 때문이다.
- 05의 편도 목표는 **방향 표결에 쓴 그 영상들로** 평가한다(같은 데이터).
- 실시간 상태 머신은 제한 시간 안에 요청 방향이 **한 번이라도** 검출되면 통과시키고
  반대 방향 검출로 즉시 실패시키지 않는다(4.1). 05의 "구간의 첫 검출" 기준은 이보다
  엄격하다. 요청을 읽고 반응하는 시간은 여전히 재지 못한다.

데이터를 더 받을 때 7장 촬영 가이드(정지 상태에서 시작, 한 방향으로 튕기고 돌아와
멈춤)를 지키면 방향 표결에 쓸 수 있는 영상이 늘어난다.

### 5.9 그 밖에

- `NEG_exit` 영상에서는 손이 빠져나가는 동안 이동이 검출된다. 실시간에서는
  `max_lost_frames`(시간 기준 1.25초) 초과로 `HAND_LOST` 처리되지만, 이동 단계는 판정되는
  즉시 넘어가므로 손이 사라지기 직전의 움직임이 이동 단계를 통과시킨다.
  **판단: 정상 이동으로 수용한다 (2026-09-16).** 웹캠 손 이탈 5회 중 3회에서 손이 사라지기
  전 이동이 인정됐는데(4.4), 인정된 방향이 **모두 손이 실제로 빠져나간 방향**이었고
  (RIGHT·LEFT·UP) 축비도 11~45(`P01_NEG_exit_05`는 4.2~4.7)로 한 축으로 뚜렷한 이동이었다.
  요청 방향으로 크게 움직이다 화면을 벗어난 것이라 방향도 맞고 판정 근거도 정상 이동과
  같다. 공격이라기보다 정상 수행으로 본다. 판정 경로에는 손 이탈을 따로 막는 규칙을 넣지
  않는다.
- 파일럿 영상은 참가자당 동작별 1개뿐이라 백분위 추정이 불안정하다.
- `timing`은 파일럿 영상의 수행 시간에서 뽑았다. 실제 사용자는 요청을 읽고
  반응하는 시간이 추가로 필요하므로 실사용 데이터로 다시 재야 한다.
- `coordinate_frame`은 실시간에서 `mirrored`, 파일럿 영상 검증에서는 `raw`다.
  파일럿 영상은 거울 반전 없이 저장됐기 때문이다.

### 5.10 이동 요청은 되돌아오는 획으로 반대 방향도 통과한다 (미해결)

대각선 목표를 요청 1회 기준으로 바꾸면서 같은 측정을 **정상 MOVE 파일럿 영상 40개**에도
해 봤다(`negative_eval.request_passes`, 제한 시간·재시도 그대로).

| 요청 방향 | 통과 |
|---|---|
| 영상 라벨과 같은 방향 | 98% |
| **반대 방향** (LEFT 영상에 RIGHT 요청 등) | **82% (33/40)** |
| 수직 방향 | 1% (1/80) |

이동은 끝나면 손이 돌아오고, 상태 머신은 반대 방향 검출로 즉시 실패시키지 않는다(4.1,
왕복 중 반대 획 때문에 정상 수행이 죽지 않게 한 설계). 그래서 돌아오는 획이 반대 방향
요청을 만족시킨다. **이동 영상 하나를 재생하면 4방향 중 같은 축 2방향이 뚫린다**는 뜻이라,
이동 단계가 방향으로 거르는 힘은 사실상 "가로/세로 축" 수준이다. 대각선(15~20%)보다 큰
구조적 약점이다.

손 모양 단계 2개가 함께 요구되므로 Challenge 전체가 뚫리지는 않지만, 이동 단계만 보면
방향 추측 확률이 1/4이 아니라 약 1/2다. 막으려면 "요청 반대 방향 획이 먼저 확정되면 실패"
같은 순서 규칙이 필요한데, 그러면 준비 동작으로 손을 반대쪽으로 빼는 정상 사용자가
실패한다. 실시간 세션에서 준비 동작이 얼마나 나오는지부터 재야 한다.

## 6. 구조

```
core/
  naming.py                 파일명 파싱. NEG를 손모양/이동/추적 반례로 분류
  landmark_io.py            영상 -> 랜드마크, 캐시 입출력, 회전·반전 정렬
  geometry.py               각도·거리·손바닥 중심. 임계값 없음
  features.py               분석과 판정이 공유하는 특징 계산. 임계값 없음
  hand_action_detector.py   손 모양 패턴 매칭
  movement_detector.py      이동 방향 판정
  challenge_generator.py    secrets 기반 무작위 Challenge 생성
  challenge_state_machine.py 순서·시간 관리. UI 프레임워크 의존 없음
scripts/
  guide_overlay.py          요청 동작 안내 패널. 판정 규칙에서 직접 생성
  hand_sketch.py            MediaPipe 21점 구조로 손 뼈대 그리기 (그림 전용)
  challenge_logger.py       세션 결과 저장 + 실행 중 사유별 통계(RunStats)
```

`challenge_state_machine.py`는 순수 파이썬이다(numpy 외 의존 없음). Flutter로
이식할 때 이 클래스가 명세 역할을 한다. 실패 사유는 문자열이 아니라 `FailReason`
enum이며, 어떤 공격이 어느 단계에서 막혔는지 집계할 수 있다.

테스트는 실제 영상 없이 **합성 랜드마크**(`tests/synth.py`)로 돌아간다. 관절 각도를
지정해 손을 만들 수 있으므로 임계값 경계 동작까지 검증한다.

## 7. 촬영 가이드 (추가 촬영 시)

**공통**
- 오른손, 손바닥이 카메라를 향하게 한다. 폰은 세로로 거치한다.
- 영상 1개에 동작 1개만 담는다.
- 파일명은 `{참가자}_{동작}_{조건}_{번호}.mp4` / `{참가자}_NEG_{종류}_{번호}.mp4`.
  확장자는 한 번만 붙인다(`.mp4.mp4`, `.MOV`는 01이 찾지 못하거나 거부한다).

**`NEG_halffist` (반쯤 쥔 손)는 두 가지 방식을 모두 찍는다.** 사람마다 쥐는 방식이
달라 한 방식만 찍으면 다른 방식의 오판정을 재지 못한다 (5.1).
1. 손가락 중간 마디를 굽히는 방식: 손가락 끝이 손바닥 쪽으로 말려 들어간다.
2. 손가락은 편 채 손바닥 쪽 관절만 굽히는 방식: 손가락이 곧은 채로 앞으로 꺾인다.

**`MOVE_*`는 중앙에서 멈췄다가 한 방향으로 튕기고 돌아온다.** 멈춤 없이 좌우(상하)로
계속 왕복하면 영상만으로 어느 방향 영상인지 알 수 없어 `direction_map`을 정하지
못한다. 영상은 손이 중앙에 멈춘 상태에서 시작한다.
